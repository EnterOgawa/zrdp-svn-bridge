# Phase 6 Hardening設計・異常系matrix

## 1. 目的

Phase 5までに成立したlocalhost HTTP Proxy、`ESVNBRG`、allowlist限定Agent
Socketの経路へ、Agent異常終了の自動検知、安全なsession再確立、slow peerの
有限timeout、および異常系の反復検証を追加する。

実取引先SVN、支給PC、Zscaler設定、Windows network設定には触れない。

## 2. 現状監査

既存実装は次をすでにfail-closedで処理している。

- frame magic、version、type、flags、stream ID、sequence、lengthの異常
- HTTP request line、Host、authority、chunked framing、header上限の異常
- stream／connection window、Frame queue、Socket queue、同時stream数の上限
- allowlist完全一致前のSocket生成禁止
- `127.0.0.1`固定bindとaccept peerのloopback再検証
- connect timeout、half-close、peer reset、RDP切断相当の全state破棄
- COM／Win32 callbackからのC++例外流出防止
- 固定event／数値fieldだけを受け付ける診断logと1 MiB・3世代rotation

不足している境界は次の二点である。

1. Agentが正常なconnection-level `CLOSE`を送れず異常終了した場合、通常の
   Proxy利用中は次の手動EchoまでClientが不在を検知できない。
2. loopback HTTP peerまたはallowlist済みupstream peerが接続後に無通信となった
   場合、buffer量は有限でもconnection枠を無期限に保持できる。

## 3. 変更方針

### 3.1 Agent health check

- Clientはhandshake成立中、5秒間隔で非空payloadのconnection-level
  `PING`を一件だけ送る。
- 15秒以内にsequenceとpayloadが一致する`PONG`を受信できなければ、旧Proxy
  streamとqueueを全破棄し、RDP画面を維持したまま`WaitingForAgent`へ戻る。
- timeout後は新しい`HELLO`を送信し、Agent再起動後に同じRDP sessionで
  handshakeを再確立する。
- handshake成立後の周期`HELLO`は送らない。health checkは既存`PING`／`PONG`
  wire formatを再利用し、Agentのactive streamをresetしない。
- 手動Echo開始時はhealth checkを停止し、Echo用`HELLO`でsequenceを明示的に
  再初期化する。
- timeoutは固定event `bridge.peer_timeout`だけを記録し、endpoint、payload、
  HTTP情報は記録しない。

Protocol version、frame layout、feature bitは変更しない。Phase 5 Agentとの
wire compatibilityを維持する。

### 3.2 slow peer timeout

- local HTTP connectionが最初の有効request headerを30秒以内に完成できなければ、
  Slowloris対策としてSocketを閉じる。部分受信で期限を延長しない。
- OPEN後を含むlocal HTTP connectionが30分間送受信とも進捗しなければ、
  `CLOSE(Timeout)`へ変換してSocketを閉じる。
- Agentの接続済みupstream Socketも30分間send／receive進捗がなければ、
  `CLOSE(Timeout)`へ変換して閉じる。
- connect完了待ちは既存の5秒を維持する。
- timeout値はproductのnetwork設定として公開せず、compile時既定値とする。
  Client workerの内部test設定だけは短い値を注入可能にする。

30分間完全に無通信のHTTP Keep-Aliveは切断される。HTTP clientは新しい
connectionで再試行できるが、途中の一操作を自動再送しない。

## 6. Security boundaryへの影響

- ActiveX／COMのversion選択、認証、RDP security設定は変更しない。
- Static Virtual Channel名とwire formatは変更しない。
- Proxy bind先は`127.0.0.1`固定のままとする。
- Agent接続先は既存allowlist完全一致のままとする。
- inbound port、DNS、OS Proxy、汎用TCP forward、`CONNECT`は追加しない。
- health payloadは固定binaryであり、endpointやcredentialを含めずlogへ出さない。

## 7. 失敗時動作とrollback

- health timer生成またはhealth Frame queueに失敗した場合、無期限にReady表示を
  維持せずBridge data planeだけを停止または新HELLO待機へ戻す。
- timeout処理で旧streamのresumeやrequest自動再送は行わない。
- 実装rollbackはhealth timer、activity timestamp、追加testを同時に戻せる。
  wire formatを変更しないため、binaryの0.5.0への差し戻しに設定migrationは不要。

- Phase 4／5／6結合testを反復し、resource counterが各session後に0へ戻ることを
  確認する。
- production listenerのWindows TCP tableを検査し、loopback以外がないことを
  再確認する。
- source、設定例、生成log、配布物文字列を監査し、実endpoint、Authorization、
  Cookie、password、HTTP payloadがないことを確認する。
